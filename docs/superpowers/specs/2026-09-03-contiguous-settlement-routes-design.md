# 连续殖民路线与海路港口补全设计

日期：2026-09-03

## 目标

本次修改补全 FFCS 自定义殖民与原版殖民之间的两个缺口：

1. 陆路殖民必须从一个实时与发起国领土相邻的目标省份开始；之后每个新省份都必须与本项目已经取得且仍由发起国控制的省份直接相邻。
2. 海路殖民按 Victoria 3 1.13 原版数值在项目启动时扣除 `100000` 财政，并在港口省份首次实际移交后建立 1 级港口。

同一州区域内与当前殖民地不连通的岛屿、飞地以及被第三方领土隔开的地块不随本项目移交。它们必须在满足新的陆路或海路条件后另行殖民。

## 不在本次范围内

- 不重新启用或接管原版殖民对象与原版地图命令。
- 不改变发起国、目标国、文化家园、殖民机构、技术、并发上限、进度、抵抗和战略利益的既有规则。
- 项目取消时不返还财政，也不归还已经合法移交的省份或拆除已经建立的港口。
- 不为理论上的任意起点预生成整套 BFS 路线；该方案会重复约 1350 万条省份记录，文件规模和加载成本过高。

## 权威数据

生成器继续以最终加载栈中的 Firefall 州区域数据库和原版 `map_data/provinces.png` 为输入。省份相邻定义保持不变：上下左右像素接触，并包含地图横向环绕；角点接触不算相邻。

海路费用与港口等级以本机 Victoria 3 1.13 的以下定义为验收基准：

- `ESTABLISH_COLONY_PORT_COST = 100000`
- `ESTABLISH_COLONY_PORT_LEVEL = 1`
- `ESTABLISH_COLONY_PROVIDE_PORT = yes`

运行脚本使用字面值 `-100000` 和 `1`，验证器负责检查它们仍与最终原版定义一致，避免依赖没有同作用域先例的 define 表达式。

## 选定架构

### 生成的邻接数据库

`tools/generate_province_phases.py` 不再为每个州输出固定的四批省份，而是输出由字面省份 ID 组成的四类调度器：

1. 陆路入口触发器：判断目标所有者的某个省份是否直接邻接发起国省份。
2. 海路入口触发器：判断目标所有者是否控制该州定义的港口省份。
3. 稳定种子效果：按省份 ID 顺序选择第一个合法陆路入口；海路只选择港口省份。
4. 连续扩张效果：只选择与当前项目省份列表直接相邻的目标省份。

所有候选省份都在执行时再次检查实时所有权。生成结果只编码地图拓扑，不缓存国家边界。

### 项目存档接口

现有 `_v1` 变量的名称和含义不变。新增两个版本化项目接口：

- `ffcs_settlement_route_v2`：`1` 表示陆路，`2` 表示海路。
- `ffcs_settlement_provinces_v2`：保存在目标 state 上的变量列表，成员为本项目已经移交给发起国的 province scope。

这两个名称加入 `AGENTS.md` 的稳定存档接口清单。项目完成或取消时必须清理它们。

采用变量列表而不是省份变量，避免给全图省份写入持久标记，也不会让同一发起国的两个项目共享扩张前沿。Victoria 3 1.13 已有 `add_to_variable_list`、`is_target_in_variable_list`、`any_in_list` 和 `clear_variable_list` 的本地先例；province scope 作为列表成员仍需游戏运行时验证。

## 入口与路线选择

共同资格条件保持现状：发起国必须是已承认或未承认国家，目标国必须是松散政权，且满足文化家园、法律、技术、疟疾、战争、破产和项目上限条件。

州选择按以下优先级判定：

1. 若生成的陆路入口触发器找到实际省份边界，则路线为陆路。
2. 否则只有在目标 state 为沿海、发起国拥有港口、目标所有者控制该州定义的港口省份时，路线才可设为海路。
3. 两种路线都不成立时，该州不可选择。

同一目标同时满足两种路线时固定选择陆路，因此不收取港口费。海路条件要求目标所有者实际控制港口省份，防止在第三方控制的港口位置创建殖民港。

项目接受时写入 `ffcs_settlement_route_v2`，并继续初始化现有项目变量和计数器。海路项目立即从发起国财政扣除 `100000`；陆路项目不再扣除现有的统一 `5000` 费用。费用是沉没成本，任何后续取消都不退款。

## 分阶段扩张

### 第一块省份

省份仍在 25 进度首次移交，而不是项目接受时立即移交。

- 陆路：按省份 ID 升序选择第一个同时满足“由原目标所有者控制”和“邻接发起国省份”的候选。
- 海路：选择州定义中的港口省份，并再次检查它仍由原目标所有者控制。

选定省份在同一个效果分支中先加入 `ffcs_settlement_provinces_v2`，随后立即移交；加入列表与移交之间不经过其他调度。如果目标 state 只剩一个省份，为保证承载项目变量的 state 在清理前不被销毁，该分支不会执行，省份移交推迟到 100 进度；这时它就是本项目的第一批也是最后一批领土。

### 后续省份

每个候选省份必须同时满足：

- 当前仍由 `ffcs_settlement_original_owner_v1` 控制；
- 至少一个真实相邻省份存在于 `ffcs_settlement_provinces_v2`；
- 该相邻项目省份当前仍由 `ffcs_settlement_sponsor_v1` 控制。

候选按省份 ID 稳定排序。省份先加入项目列表，再由州区域作用域执行单省 `set_owner_of_provinces`。一个阶段反复扫描当前州区域，直到达到阶段预算、没有合法前沿，或目标 state 只剩一个省份。

阶段预算以该阶段开始时目标 state 的当前省份数计算：

`ceil((num_provinces - 1) / remaining_phase_count)`

25、50、75、95 四个阈值的 `remaining_phase_count` 分别为 4、3、2、1。第一块种子计入 25 进度阶段的预算。预算只限制节奏；如果项目连续前沿提前耗尽，阶段立即停止，不会转移到另一连通块。

95 进度后尽量只保留最后一个省份，以维持项目 state。100 进度时先保存州区域、发起国、原所有者和路线值，减少项目计数并移除项目修正，但暂时保留路线与省份列表。随后移交仍与项目列表连续的最后省份；若列表尚未建立，则重新运行当前路线的种子选择器。最后在仍存在的目标 state 上清理路线、列表和其余项目变量；若目标 state 因最后一次移交而消失，其变量随 scope 一并消失。其他不连续省份留给原所有者。

完成后只对发起国在该州区域中的 state 执行必要的未建制状态处理；已经建制的 state 不降级。项目产生的新 state 保持未建制状态。

## 海路港口

海路种子省份实际移交后，在发起国对应的 region state 上检查 `building_port`：

- 不存在港口时创建 1 级 `building_port`；
- 已存在港口时不增加等级；
- 首块省份尚未移交时不建港；
- 单省州在 100 进度实际移交后建港。

这样港口建筑与港口省份所有权同时出现，不会在目标国领土中提前创建发起国港口。

## 持续有效性与取消

战略利益仍只在项目启动时检查，之后失去战略利益不取消项目。

项目每月必须拥有 `ffcs_settlement_route_v2`。没有该变量的旧版活动项目视为不可安全迁移，在下一次月度检查时取消；既有移交领土保留。

首块尚未取得时：

- 陆路必须仍存在合法的实时省份边界；
- 海路必须仍满足发起国拥有港口、目标 state 沿海、港口省份仍由原目标所有者控制。

首块取得后：

- 至少一个项目列表省份必须仍由发起国控制；
- 海路项目还要求港口省份仍由发起国控制、对应 state 仍有港口建筑且发起国仍拥有港口能力。

若项目列表中的部分省份被夺走，后续扩张不能再以这些省份为前沿。全部项目省份丢失即立刻取消。若当前连续地块已经完整取得而同一目标 state 仍有其他断开地块，项目可以继续走完进度并正常完成，但不会取得那些断开地块。

取消继续使用现有行为：减少双方计数器、移除修正和所有项目变量、发送取消通知，不退款、不回滚领土、不拆港。

## 存档迁移

旧存档中的 `_v1` 项目没有可靠的首块与扩张前沿记录，无法证明已移交省份连续。为避免猜测或重写玩家领土，迁移策略固定为：

- 下一次月度调度发现缺少 `ffcs_settlement_route_v2` 时取消旧项目；
- 正常减少活动与入境项目计数；
- 保留旧项目已经移交的领土；
- 不返还旧费用。

新项目的路线与省份列表必须通过保存/读取保持不变。

## 生成规模与性能

生成内容按省份数和邻接边数线性增长，不为每个种子复制完整路线。阶段效果只在 25、50、75、95 和最终收尾时扫描目标州区域，不增加新的月度全图遍历。

动态前沿扫描在狭长、ID 顺序不利的大州中最坏可能重复扫描同一批候选，复杂度可到该州省份数的平方。当前项目并发受殖民机构上限约束，先保留这一简单实现；只有运行时性能证据显示阶段结算卡顿时，才引入更复杂的生成顺序优化。

## 验证

### 生成器与静态验证

- 所有生成候选与前驱必须是 `provinces.png` 中真实相邻的省份。
- 邻接关系必须对称，且横向环绕行为保持不变。
- 每个港口种子必须属于对应州区域。
- 每个转移分支必须检查原目标所有权和项目列表前驱。
- 陆路种子分支必须检查发起国实际拥有相邻省份。
- 生成器连续运行两次，生成文件和 manifest 的哈希必须一致。
- manifest schema 升级并记录州区域数、省份数、邻接边数、港口种子数、断开州区域数和输出哈希。
- 验证器只统计 `set_owner_of_provinces` 的目标，不把邻接判断中重复出现的省份字面量误判为重复转移。
- 继续检查 JSON、Paradox Script 括号和引号、owned 顶层 ID 唯一性、英文与简体中文本地化键集合和 BOM、最终上游 AI 表以及 `git diff --check`。
- `.metadata/metadata.json` 的版本提升为 `0.3.0`。

### 游戏运行时验证

1. 陆路项目的第一块目标省份与发起国省份实际相邻。
2. 每个后续省份与该项目此前取得且仍由发起国控制的省份相邻。
3. 同一发起国在同州另一侧的领土不会成为第二起点。
4. 同州岛屿、飞地和第三方阻隔地块保持不变。
5. 海路接受项目时财政准确减少 `100000`，取消不退款。
6. 海路港口省份先移交，随后出现且仅出现 1 级港口；首块前取消不建港。
7. 单省州不会提前销毁项目 state，最终移交和建港正常完成。
8. 失去实际路线立即取消；仅失去战略利益不取消。
9. 保存并读取后，路线、项目省份列表、阶段与进度保持一致。
10. 缺少 v2 路线的旧活动项目在月度调度时安全取消并正确回收计数器。

运行时日志继续区分文件加载、顶层解析、月度调度、资格判断、种子移交、阶段转移、取消和最终状态。province scope 作为变量列表成员必须由无脚本错误的实际种子与后续扩张日志证明；若该接口在 1.13 运行时不接受 province scope，停止交付并改用预生成逐起点路线方案，不以静态通过代替运行证明。
